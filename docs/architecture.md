# Architecture – TestAcer

_Status: proposed · 2026-11-21_

## Components

```
Flutter app (one codebase) ──┬─ web build ──────► GitHub Pages (static files)
                             └─ Android build ──► testers' phones (APK)
        │
        ├─ Firebase Authentication  (email/password, email link, Google)
        ├─ Cloud Firestore          (question sets, settings, progress; offline cache)
        └─ Android only: flutter_local_notifications + timezone + workmanager
                         (scheduled reminders, notification action buttons)
```

There is no custom server. Everything runs in the app plus Firebase's managed services, within the no-cost Spark plan.

## Code structure

```

├─ firebase_options.dart          generated by flutterfire
├─ l10n/                          app_hu.arb + generated AppLocalizations
└─ src/

   ├─ config.dart                 web app URL, Android package
   ├─ localization.dart           delegate list (see note below)

   ├─ auth/                       AuthService interface + Firebase implementation,
   │                              e-mail link controller and store, models
   ├─ access/                     AccessRepository interface + Firestore allowlist
   ├─ question_format/            Markdown question parser (Phase 1)
   ├─ questions/                  QuestionSetRepository + Firestore codec
   ├─ quiz/                       progress records, Leitner picker, QuizSession, QuizClock,
   │                              ProgressRepository
   ├─ settings/                   UserSettings (active set, quiz length, reminders)
   ├─ reminders/                  reminder settings, planner, snapshot store,
   │                              notifications wrapper, service, background job
   ├─ import/                     file picker wrapper
   └─ ui/                         gate, sign-in, status, home, quiz, progress,
                                  import, invitations, reminder settings screens
```

- Services are interfaces (`AuthService`, `AccessRepository`, `EmailLinkStore`); widget tests use fakes from `test/support/fakes.dart`, so no Firebase is needed in `flutter test`.
- UI code imports `package:material_ui/material_ui.dart`: since Flutter 3.47 Material is a separate package. Its localisations are `material_ui`'s and `cupertino_ui`'s own `Global…Localizations`; the list generated by `flutter gen-l10n` still uses the deprecated copies in `flutter_localizations`, so the app uses `appLocalizationsDelegates` from `localization.dart` instead.

## Data model (Firestore)

```
allowlist/{email}                      { invitedAt, role: "admin" | "learner" }
questionSets/{setId}                   { title, sourceFile, importedAt, questionCount, trivia: [ { title, body, keywords[] } ] }
questionSets/{setId}/questions/{key}   { order, prompt?, correct: { text, marks[] }, wrong: [ { text, note? } ], previousKeys[]? }
users/{uid}                            { displayName, email, activeSetId, settings { … } }
users/{uid}/progress/{setId}           { items: { <key>: { box, seen, correct, wrong, lastAt, skippable } } }
```

- `key` – stable hash of the normalised correct-answer text ([question-format.md](question-format.md#question-key)), so re-importing an edited file keeps progress for unchanged questions.
- `marks[]` – emphasis ranges of the correct answer (`subject`, `differs`); used only in the feedback view.
- `previousKeys[]` – keys a question had before its correct answer was edited (same number, D-017). Progress is not rewritten: when the quiz, the Haladás page or the reminders load a user's progress, a question without a record under its key takes the record of its newest previous key (`carryOverProgress`); new answers are saved under the current key.
- `trivia` – the „Tudtad?” items of the set's file (D-016), read once when a quiz starts; after each answer the items whose keywords occur in the correct option are shown in a bottom sheet.
- Progress for a whole set is **one document** (149 small entries, roughly 15 KB): one read when a session starts, far below the free daily quota.
- `settings`: `quizLength` (`five`, `ten`, `twentyFive`, `all` = „Mind”, D-020; a stored `one` or `endless` reads as `ten`; `endless` is only used for quizzes opened from a reminder), `notifications { enabled, mode: "open" | "trueFalse", windows: [ { days: [1..7], start: "09:00", end: "22:00", everyMinutes: 60 } ] }` (Monday = 1; `end` is the last reminder of the day; `mode` is used from Phase 6).
- Progress records store `lastAt` as milliseconds since the epoch (the quiz code stays plain Dart).
- Writes are not awaited by the UI: offline, Firestore completes a write only after reconnecting, but the local cache (also enabled on the web) already has it.

## Security rules (sketch)

```
function invited() {
  return request.auth != null
    && (request.auth.token.email_verified || request.auth.token.firebase.sign_in_provider == "google.com")
    && exists(/databases/$(database)/documents/allowlist/$(request.auth.token.email));
}
function admin() {
  return invited()
    && get(/databases/$(database)/documents/allowlist/$(request.auth.token.email)).data.role == "admin";
}

match /questionSets/{rest=**} { allow read: if invited(); allow write: if admin(); }
match /users/{uid}/{rest=**}  { allow read, write: if invited() && request.auth.uid == uid; }
match /allowlist/{email}      { allow read: if request.auth.token.email == email || admin();
                                allow write: if admin(); }
```

The Firebase web configuration in the (public) repository is not a secret. Access is controlled by these rules and by the Auth authorised domains.

## Sign-in

| Method | Web | Android | Notes |
|---|---|---|---|
| Email + password | ✔ | ✔ | the e-mail must be verified before access |
| Email link (passwordless, D-013) | ✔ | ✔ | the link returns to the web app URL; on Android it opens the app via App Links on `<project-id>.firebaseapp.com/__/auth/links`; signing in with it verifies the e-mail |
| Google | ✔ (popup) | ✔ | Android needs the SHA fingerprints in Firebase |

- One account per e-mail address (Firebase's default setting): the methods are alternative ways into the same account.
- The email link is sent with `ActionCodeSettings`: `url` = the web app address (GitHub Pages), `handleCodeInApp: true`, Android package `com.airdeux.testacer`. The address the link was sent to is kept locally, so a link opened on the same device signs in without asking again.
- The GitHub Pages domain must be in the Auth authorised domains (also needed for Google sign-in on the web).
- On Android the link opens the app only if `https://testacer-892b3.firebaseapp.com/.well-known/assetlinks.json` names `com.airdeux.testacer` and its SHA-256 fingerprint. That file is served by a minimal Firebase Hosting site (`firebase/hosting`, no-cost); without it the link opens in the browser and signs in on the web app instead.
- Screens: signed out → sign-in; unverified password account → verify e-mail (the ID token is refreshed after verification, because the rules read `email_verified` from it); signed in → allowlist check → not invited / home. The allowlist entry is watched live, so an invitation lets a waiting user in without reloading.

## Quiz flow

1. Load the active set (cache first, then Firestore) and the user's progress document.
2. Pick the next question (D-006): leave out skippable questions and the last 5 asked; weighted random by Leitner box – box 0 → 8, box 1 → 4, box 2 → 2, box 3 → 1, box 4 → 0.5. Unseen questions start in box 0. In a quiz of more than one question every other question (1st, 3rd, 5th…) is instead the least-seen one – never seen first, random among equals – so at least half of the quiz is new (D-015).
3. Show the question with the 4 options **shuffled** and **without emphasis** (emphasis would give the answer away, D-007).
4. After the answer: right/wrong, then the correct answer with emphasis (***subject***, **differs**) and any note. Correct → box + 1 (max 4); wrong → box 0.
5. "Skippable" toggle on the feedback view; undo from the progress view.
6. Continue until the chosen quiz length is reached, or until the user closes the quiz (endless mode).

## Reminders (Android)

### Why a rolling schedule

- An Android notification is built completely – title, text, buttons – **at the moment it is scheduled**. When it pops up later, the app does not run; Android just shows what it was given.
- `flutter_local_notifications` can repeat a notification every day at a fixed time, but then it repeats the **same content**: a daily 09:00 reminder would show the same question every morning.
- For answering in the notification the question must already be inside the notification, so it has to be chosen in advance.

So the app schedules **one-off notifications, each with its own pre-picked question**, a few days ahead, and re-plans them whenever it gets a chance to run.

Example – window: every day 09:00–22:00, every 60 minutes (14 reminders a day); the plan is made on Saturday at 15:49:

| Slot | Question picked at planning time |
|---|---|
| Sat 16:00 | #37 |
| Sat 17:00 | #102 |
| … | … |
| Sat 22:00 | #8 |
| Sun 09:00 | #55 |
| … | … until 48 slots are filled (about 3½ days) |

- **Planner** (`lib/src/reminders/planner.dart`) – computes the next 48 slots from the windows in Europe/Budapest time (`timezone` package; a 09:00 reminder stays at 09:00 local time across daylight-saving changes), picks a question for each with the selection engine (D-006: skippable never, no repeats among the 48 while enough questions are left), and schedules them with `zonedSchedule` (inexact, allowed while idle). Notification id = minutes since the epoch of the slot, so a re-plan never collides with a reminder already on screen.
- **Re-planning** – cancels the slots that have not been shown yet (`cancelAllPendingNotifications`; shown ones stay) and plans them again: when the home page opens, when the active set or the reminder settings change, after every quiz, after each answer given in a notification (Phase 6), and from a background job every 12 hours (`workmanager`). After a reboot or an app update the plugin's boot receiver restores the scheduled reminders. A time-zone change needs nothing: slots are absolute instants computed in Europe/Budapest. Signing out cancels everything. This keeps the picks fresh: a question answered right in the meantime moves to a higher box, and one marked skippable drops out.
- **Snapshot on the phone** – the background job runs without Firebase, so each sync stores the active set's questions, the progress and the settings in shared_preferences (`ReminderSnapshot`). Questions are read from Firestore again only when the set changes (its `importedAt`), progress on every sync (one document).
- **Content** – title „Jöhet egy kérdés?”; no text, unless the question has a prompt. Not the ***subject***: in some questions it gives the answer away (e.g. „dojo”). Channel „Emlékeztetők”, high importance; status-bar icon `res/drawable/ic_stat_reminder.xml` – the app icon's „A” mark in white, generated by `tool/branding/make_icons.py` (kept in release builds by `res/raw/keep.xml`).
- **Settings** – `users/{uid}.settings.notifications` (synced; each phone plans its own): on/off, windows (days, first and last time, every 15 min – 4 h). Screen: **Emlékeztetők** on the home page (Android only), with a test notification and a battery-optimisation hint.
- **If the app cannot run for days** (phone off, background job blocked by an aggressive battery saver), reminders continue until the last planned slot and then pause until the app is opened again.
- **Why 48** – Android limits how many alarms one app may have scheduled (roughly 500); 48 covers several days with a wide margin.
- **Alternative considered** – wake the app at every slot (`android_alarm_manager_plus`) and pick the question right then. That always uses the latest progress, but it starts the Flutter engine in the background every hour, and battery savers stop such jobs more often. Can be revisited if the rolling schedule is not good enough.
- **Tap** on the notification body → the app opens an endless quick quiz starting with that question. The notification payload is `{"set": <setId>, "q": <key>}`; a tap that starts the app is read with `getNotificationAppLaunchDetails`, one while it runs arrives through the plugin's callback; the home page opens the quiz once the sets are loaded.
- **Permissions** – `POST_NOTIFICATIONS` (asked when reminders are switched on or a test is sent, Android 13+), `RECEIVE_BOOT_COMPLETED`. No exact-alarm permission: it is restricted on recent Android versions and not needed for hourly reminders (a few minutes' delay is acceptable).
- **Build requirements** – `flutter_local_notifications` 23 needs core library desugaring and `compileSdk` ≥ 37 (`android/app/build.gradle.kts`).

### Answering in the notification (mode `trueFalse`, D-005)

Android shows at most 3 action buttons, so the notification shows **one statement** – either the correct option or a random wrong one – titled „Igaz vagy hamis?”, with no other text (the expanded notification shows a long statement in full), and the buttons **Igaz** / **Hamis** / **Összes válasz**.

- **Statement** – chosen at planning time, half and half the correct option or one of the wrong ones (so „Igaz” and „Hamis” are equally often right); stored in the payload as `"w"` (`-1` = correct option, otherwise the index of the wrong option): `{"set", "q", "w"}`.
- **Igaz / Hamis** – actions without UI (`cancelNotification: false`), handled by `reminderActionInBackground` (`@pragma('vm:entry-point')`, `lib/src/reminders/reminder_setup.dart`) in the plugin's background isolate, without opening the app and without Firebase: the copy of the progress in the snapshot is updated, the answer is added to a queue in shared_preferences (`QueuedAnswer`: uid, set, key, right or wrong, time), the same notification is replaced – quietly (`onlyAlertOnce`) – by the result (title „✔ Helyes!” / „✘ Nem jó”; text: „Helyes: …” with the correct statement unless „Igaz” was rightly said to it, then „Következő – igaz vagy hamis?” and the next statement) **plus the next statement** with the buttons again (a series until the user dismisses it), and the remaining slots are re-planned. A correctly judged statement counts as a correct answer for its question. If the app happens to run, the plugin delivers the press to the main isolate instead; the same code handles it and writes to Firestore at once.
- **Összes válasz** – the action opens the app (`showsUserInterface: true`) on the quick quiz starting with the same question: its 4 options shuffled, single-select, the usual feedback (emphasis, note, skippable toggle), **Következő**, and ✕ to close. This is the same page a tap on the notification opens; a separate dialog would have duplicated it (D-005 note).
- **Queue sync** – on the next sync (home page, after a quiz) the queued answers of the signed-in user are replayed in order on the record read from Firestore (counters add up, the box moves; a later `lastAt` from an answer in the app is kept) and written; if Firestore cannot be read, they go back to the queue. Other users' answers stay queued.
- The question set is cached on the device (the snapshot), so the background handler never needs the network.
- **Android** – the plugin's `ActionBroadcastReceiver` is registered in `AndroidManifest.xml`.

## Web

- `flutter build web --release --base-href /testacer/`, deployed to GitHub Pages by `.github/workflows/deploy-web.yml`. It runs after the *CI* workflow passes for a push to `main` (`workflow_run`), builds the commit CI tested, and publishes with `actions/upload-pages-artifact` + `actions/deploy-pages` (or by hand: *Run workflow*).
- Flutter's default hash URLs (`…/testacer/#/quiz`) avoid 404 errors on reload, which GitHub Pages cannot rewrite.
- `airdeux.github.io` is in the Firebase Auth authorised domains; Google sign-in uses a popup.
- Address: https://airdeux.github.io/testacer/ (also `webAppUrl` in `lib/src/config.dart`, the return address of sign-in links). The path is the repository name and GitHub Pages treats it case-sensitively, so the repository is named `testacer` in lower case.
- No reminders on the web in the MVP: that would need FCM web push plus a server-side scheduler.

## Later: server-side push (FCM)

Firebase Cloud Messaging itself is no-cost, but scheduled pushes need something that runs on a timer: Cloud Functions (requires the Blaze plan, i.e. a billing account with a payment method) or an external cron job (e.g. a scheduled GitHub Actions workflow, which is not punctual). It is only worth adding for web reminders or for messages to all users ("new question set available").
